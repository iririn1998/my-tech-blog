React Server Components(以下 RSC)をプロダクションに入れてから半年が経ちました。導入前に読んだ解説記事と、実際の運用で起きたことの間には、それなりの距離があります。本稿では、その距離を埋めるために書き留めてきたメモを整理してお届けします。

## 導入の背景

対象はページ数およそ200の管理画面です。初期表示のバンドルサイズが1.2MBを超え、ダッシュボードの表示に体感で2秒以上かかる状態でした。データ取得ロジックの大半がクライアント側にあり、ウォーターフォールが常態化していたのが主因です。

RSC の採用を決めた理由は、書き直しではなくページ単位の漸進的な移行が可能だったことに尽きます。ルーティング単位で切り替えられるため、リスクの低い設定画面から着手しました。

## データ取得の境界を引く

最初の設計判断は「どこまでをサーバーコンポーネントにするか」です。結論から言うと、`page.tsx` と一覧・詳細のコンテナまでをサーバー側とし、フォームと対話的な部品だけをクライアントに残しました。

```tsx
// app/projects/page.tsx — サーバーコンポーネント
export default async function ProjectsPage() {
	const projects = await db.project.findMany({
		orderBy: { updatedAt: 'desc' },
	});
	return <ProjectList items={projects} />;
}
```

この境界を一度決めてしまえば、迷いはほとんどなくなります。逆に境界を都度判断していたチームは、レビューのたびに議論が発生していました。指針は文書化して共有する価値があります。

## つまずいたポイント

最大のつまずきはシリアライズ境界でした。サーバーからクライアントへ渡せるのはシリアライズ可能な値だけです。Date や Decimal をそのまま渡してランタイムエラーになるケースが、移行初期に頻発しました。

```tsx
// 境界を通す前に DTO へ詰め替える
function toProjectDto(p: Project): ProjectDto {
	return {
		id: p.id,
		name: p.name,
		updatedAt: p.updatedAt.toISOString(), // Date は文字列に
	};
}
```

境界を通るデータはすべて DTO に詰め替える、という規約を入れてからはエラーが消えました。型で強制できるため、レビューの負担も増えていません。

## 成果と数字

移行完了したページ群では、クライアントバンドルが1.2MBから420KBへ、LCP の中央値が2.4秒から1.1秒へ改善しました。数字以上に大きいのは、データ取得コードがサーバー側に集約されて見通しがよくなったことです。

## まとめ

RSC は「速くなる技術」というより「データ取得の置き場所を正す技術」でした。境界の指針を先に文書化し、DTO 詰め替えを規約にする。この2点を先に済ませておけば、移行は思ったより静かに進みます。
